
# 💡 LoRa 通信“能发不能收”技术笔记

### 1. 核心诱因：RTOS 栈溢出与内存踩踏

**原理：**

在 Zephyr 中，每个线程（如你的 `lora_test_task`）都有独立的栈空间。

- **局部变量风险**：当你将 `rx_buf` 定义在 `while(1)` 内部时，它会被分配在线程栈上。
    
- **栈深度压力**：LoRa 驱动在执行 `lora_recv` 时，会调用一系列底层 SPI 通信、中断处理和缓冲区操作。这些函数调用链会消耗大量栈深度。
    
- **踩踏现象**：如果线程栈（你设置的是 2048 字节）在运行过程中接近临界点，`memset` 或驱动写入 `rx_buf` 的操作极易踩到线程的“预警区（Guard Region）”或者破坏了函数返回地址。这会导致程序逻辑虽然没死机，但某些变量（如 `len` 或 `config`）的值被悄悄篡改，导致 `if(len == 5)` 逻辑永远不成立。
    

### 2. 局部变量的初始化时机（栈重用）

**原理：**

在 C 语言中，`while` 循环内部的局部变量在每一轮循环中逻辑上是“新鲜”的。

- 在 RTOS 任务中，编译器可能会优化栈帧，导致 `rx_buf` 的内存地址在某些复杂的内核调度（如 `k_sem_take` 挂起后恢复）过程中发生不可预知的变化。
    
- 使用 **全局静态变量**（或 `static` 局部变量）会将数据存储在 **.bss/.data 段**，这部分内存是永久分配且地址固定的，彻底消除了驱动程序（异步 DMA 或中断）写入数据时地址失效的风险。
    

### 3. LoRa 驱动的状态机冲突

**原理：**

LoRa 芯片（如 SX126x/SX127x）是半双工硬件。

- **TX/RX 切换代价**：`lora_send` 会将芯片切入发送模式并拉高 PA（功率放大器）。发送完成后，硬件处于 `STANDBY` 或 `TX_DONE` 状态。
    
- **配置覆盖**：你提到的 `tx=true` 和 `tx=false` 必须分别配置。这是因为驱动内部对 TX 和 RX 的某些寄存器（如 IQ 极性、Sync Word、甚至电源 LDO 设置）是分别处理的。
    
- **如果配置丢失**：当栈溢出踩掉了你的 `config` 结构体，`lora_recv` 可能会以错误的参数（比如错误的 SF 或频率）去配置硬件，导致物理层无法锁定信号。
    

### 4. 时序竞争 (Timing Race Condition)

**原理：**

- **Node 侧**：发送完成后到进入 `lora_recv` 之间存在一段“盲区”。
    
- **Target 侧**：收到数据后立即回传。
    
    如果 Node 侧因为线程优先级较低或任务调度延迟，导致 `lora_recv` 调用的时间晚于 Target 发出数据包的 **Preamble（前导码）** 时间，Node 将错过整个数据包。全局变量减少了栈操作开销，可能微弱地提升了进入接收模式的速度。
    

---

### 🛠️ 专家建议总结：LoRa 开发黄金准则

|**现象**|**可能原因**|**解决方案**|
|---|---|---|
|**能发不能收**|缓冲区在栈上导致溢出|**将 RX Buffer 改为全局变量或 `static`。**|
|**偶尔收不到**|收发模式切换太慢|**确保对端（Target）有 100ms+ 的回复延迟。**|
|**长包收不到**|缓冲区太小|**缓冲区长度应 $\ge$ 255 字节（LoRa 最大载荷）。**|
|**逻辑正常但超时**|配置参数被覆盖|**每次收发前显式检查 `lora_modem_config` 的完整性。**|
